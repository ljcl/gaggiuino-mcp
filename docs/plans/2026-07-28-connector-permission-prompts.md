# Claude keeps asking permission for this connector

## The symptom

On Claude for iOS, this connector prompts for approval on tool calls that were
already set to "always allow" on the web. Logging out and back in does not fix
it; neither does re-setting the connector-level toggle.

## What is and is not this server's fault

Three mechanisms can produce that symptom. Only one of them lives here.

1. **Host-side persistence.** There is an open, unresolved bug in Claude's
   connector permission layer where a connector-level "allow always" is not
   reliably written through to the per-tool state the runtime checks, and where
   toggling a connector inside a live chat resets tools back to "needs
   approval". Personally-owned connectors appear to be the affected class.
   Nothing this server does changes it.
2. **Host-side configuration.** Permissions are ultimately **per-tool**, and the
   connector-level toggle is a bulk action that does not always flip every
   underlying tool. An org-provisioned connector can also be capped at "needs
   approval" by a role, which removes "always allow" from the personal menu
   entirely.
3. **The advertised tool surface changing under the grant.** A host stores the
   grant against a tool's advertised identity — name, and by inference its
   schema — not against the connector as a whole. A self-hosted server that
   redeploys with a changed tool set can leave the stored grant pointing at
   something that no longer matches. **This one is ours.**

## What changed here

Only (3) is actionable in this repo, plus making sure this server is not
independently triggering a prompt by how it describes itself.

- **`apps/server/src/tool-contract.json`** — the advertised `tools/list`
  surface, committed, and asserted by `server.test.ts`. The point is not to
  freeze the tools; it is that the surface cannot change *without anyone
  noticing*. The advertised JSON Schema is generated by `z.toJSONSchema` from
  the zod schemas the dispatcher enforces, so a routine `zod` or SDK bump can
  reshape every input schema without a line of this repo changing — which would
  have shipped as an invisible grant invalidation. Regenerate deliberately with
  `bun run generate-tool-contract`; the diff is the list of grants existing
  installations lose.
- **`_meta["anthropic/requiresUserInteraction"]` is asserted absent.** That flag
  falls through to the permission prompt in every mode, offers no "don't ask
  again", and is not skipped by an existing allow rule. Every tool here reads,
  so nothing warrants it. The assertion exists because setting it is a one-line
  mistake with an unbounded blast radius.
- **`listChanged` and `resources.subscribe` are asserted unclaimed.** Every list
  this server serves is a module-level constant. Claiming `listChanged` would be
  a promise to tell the host to re-fetch, and a re-fetch is what re-keys the
  cached tools a grant is stored against.
- **Annotations are verified over the real transport.** `server.test.ts` checks
  them across an in-memory pair; `http.test.ts` now checks them again on a
  `tools/list` that crosses `WebStandardStreamableHTTPServerTransport`.
  `annotations` and `_meta` are precisely the fields a transport or SDK version
  is free to drop, and a tool that arrives without `readOnlyHint: true` is
  treated as write/destructive and prompts on every call regardless of how the
  connector is configured.
- **`session.opened` names the client.** It carries `client`, `clientVersion`,
  and `protocolVersion` now. One `session.opened` per turn from the same client
  is the signature of a host discarding its session between turns; a single
  record reused across many `tool.call` records is the healthy shape. Without
  this there was no way to tell the two apart from the server side.

The annotations themselves were already correct — every tool is
`readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, with
`openWorldHint` the only honest variation. That has not changed and should not:
`openWorldHint: true` on the tools that reach the machine is true, and lying
about it to influence a host's grouping would be exactly the kind of dishonest
annotation the rest of this server avoids.

## What is left for the operator

None of this can fix a grant that the host never persisted. On claude.ai (web —
connectors cannot be managed from iOS at all):

1. Open the connector and set permissions at the **per-tool** level, not just
   the connector toggle. Confirm nothing is left on "needs approval".
2. Set the connector's tool-access mode to **always available** rather than
   on-demand.
3. Start a **new** conversation on iOS afterwards, and do not toggle connectors
   inside a live chat — that is the reported reset path.
4. If it persists, remove and re-add the connector on the web, re-grant per
   tool, and test in a fresh chat.
5. Check whether the account is inside a managed org and whether the connector
   is org-provisioned. If the per-tool menu has no "always allow", that is an
   admin policy, not a bug.

## An open question

`get_shot_raw_json` is app-visibility only (`_meta.ui.visibility: ["app"]`), and
the shot-graph app calls it on every render. If a host prompts per app-initiated
tool call *and* hides app-only tools from its permission settings, the user
would have no way to pre-approve it and every graph render would prompt — which
would match the symptom exactly.

That is a hypothesis, not a confirmed cause, and the fix would not be free: the
tool exists precisely so hundreds of raw datapoints stay out of the model's
context. Moving them into `view_shot_graph`'s result would undo that, and the
"compare previous" path still needs a live tool call regardless. If the
server-side logs show `get_shot_raw_json` calls arriving whenever the user
reports a prompt, that is the signal to revisit it.
